# FGallery — ТЗ на следующий цикл доработок

Версия ТЗ: 1.0 · 27.10.2026
Основа кода: ветка `feature/fgallery-0.2.9-s23-qa` (последняя опубликованная версия 0.2.9, versionCode 11).
Устройство пользователя: Samsung Galaxy S23, Android 16.

Документ составлен по итогам анализа кода FGallery 0.2.9, разбора APK QuickPic 9.7 и обсуждения с пользователем. Разделы с пометкой **СОГЛАСОВАНО** утверждены пользователем: цели, поведение и критерии приёмки менять без его подтверждения нельзя; технические детали реализации можно уточнять, сообщив об этом. Разделы с пометкой **РЕШЕНИЕ НЕ ПРИНЯТО** не реализуются. Открытые вопросы — раздел 6.

## 0. Общие правила работы

1. **Ничего из работающего не ломать.** Особо охраняется:
   - открытие RAW, в том числе Phase One P65+ `.IIQ` (сейчас работает через LibRaw — этот путь остаётся запасным во всех изменениях);
   - TIFF (включая ~350 МБ из RAW), DNG, PDF, SVG, GIF, видео, 360°;
   - режим уборки (двойной тап → корзина FGallery), корзины на каждом носителе, восстановление;
   - USB/SD: подключение/отключение, запоминание отключённых носителей;
   - перемещение, переименование, кадрирование (RAW — только копия).
2. **Один этап — одна версия.** Каждый этап (раздел 2) выпускается отдельной сборкой с новым versionName/versionCode, чтобы пользователь мог проверить и откатить изменения по отдельности.
3. **Готово = проверено на устройстве.** Задача не закрывается по факту «код добавлен» или «CI зелёный». Статус в `docs/PROJECT_STATUS.md`: «в коде» → «CI пройден» → «проверено пользователем на S23».
4. **Тесты.** На каждое изменение — JVM- и/или инструментальные тесты; существующие тесты не удалять, а обновлять, если меняется согласованное поведение (например, формула зума).
5. **Документация.** После каждого этапа обновлять `docs/PROJECT_STATUS.md`, `docs/OPEN_BUGS.md`, `docs/PRODUCT_SPEC.md`, `docs/UX_RULES.md`, `docs/ZOOM_BEHAVIOR.md` — коротко: что изменено, коммит, сборка, что проверить.
6. **Секреты не в репозитории.** Ключи подписи, пароли, токены — только в GitHub Secrets.
7. **QuickPic.** Код QuickPic не копируется и не восстанавливается (он зашифрован DexProtector; обходить защиту нельзя). Из QuickPic берутся только принципы, описанные в этом ТЗ.
8. **Лицензии.** Новые зависимости — только с совместимыми лицензиями (Apache 2.0, MIT, BSD, LGPL для отдельных библиотек). Форк AndroidLibRaw (LGPL-2.1) остаётся открытым отдельным репозиторием.
9. **Существующие блокеры.** Пункты FG-01…FG-09 из `docs/PROJECT_STATUS.md` остаются в силе. Если пользователь сообщает о регрессии в них — она идёт впереди этапов этого ТЗ.

## 2. Этапы

### Этап 1 (0.3.0)

#### 1.1 Зум: второй двойной тап — СОГЛАСОВАН МЕТОД
**Проблема.** `ui/ZoomLevels.kt`: `second = base + (max - base) * .85f`, где `max = maxOf(8f, fit * 8f)` (800% от пикселей файла). Для Canon 5DS R на S23 (fit ≈ 12,4%) это 682%. Масштаб воспринимается глазом по удвоениям: 682% — это ~96% пути от «по экрану» до 800%, на щипок остаётся ×1,17, после «резинки» всё возвращается к 800%. Пользователь воспринимает второй тап как зум «в упор». Пользователь также сообщает, что после второго тапа щипком дальше увеличить не удаётся вообще — это нужно проверить индикатором (см. ниже).

**Решение.** Считать второй шаг по доле пути в удвоениях (логарифмически):
```
first  = fit * 2                       (без изменений)
second = fit * (max / fit) ^ p         p подбирается: 0.80 / 0.85 / 0.90
max    = maxOf(8f, fit * 8f)           (без изменений, щипок до 800%)
```
Ориентиры для 5DS R при p = 0.85: второй тап ≈ 430%, запас для щипка ≈ ×1,9. Малые изображения (если `first >= second`): цикл «по экрану → ×2 → по экрану» (как сейчас).

**Тестовая сборка (временно):**
- индикатор масштаба на экране просмотра: «сейчас N% · максимум 800%» (N — масштаб относительно пикселей файла);
- переключатель p = 80 / 85 / 90% в настройках (раздел «Тест»).

Пользователь выбирает p на реальных кадрах (5DS R, фото с телефона, вертикальные кадры). После выбора p фиксируется в коде, индикатор и переключатель убираются.

**Если индикатор покажет, что второй тап сразу даёт 800%** — это отдельная ошибка; найти причину (версия, устройство, единицы масштаба) до выбора p.

**Обновить:** `ZoomLevelsTest`, `TiffImageTest` (сейчас ожидает 85% линейного диапазона), тест второго шага PDF; добавить инструментальный тест «после второго тапа щипок увеличивает масштаб до максимума». PDF/SVG — по той же формуле в своих единицах (F = 1, M = 8).

#### 1.2 Метла и режим уборки — СОГЛАСОВАНО
- Сейчас: `GalleryScreen.kt` — `Text("🧹")` (цветной эмодзи среди монохромных иконок Material).
- Включение режима — только через меню, с подтверждением: «Двойной тап будет сразу отправлять файл в корзину FGallery. Включить?» [Отмена] [Включить].
- Пока режим включён — в шапке иконка `Icons.Outlined.CleaningServices`, 24dp, цвет `#FF5A36` (как рамка уборки). Тап по ней — выключение без вопросов.
- Когда режим выключен — иконки нет.

#### 1.3 Видеоплеер — СОГЛАСОВАНО
**Сейчас:** три независимых слоя — верхняя панель Compose (fade), стандартный контроллер Media3 (свои иконки и анимация, подвинут через `translationY` на `exo_progress`/`exo_position`), имя файла — отдельный `Text` с подобранными отступами (23dp/7dp), появляется без анимации и без подложки.

**Нужно:** своя панель на Compose (`androidx.media3:media3-ui-compose`), стандартный контроллер Media3 убрать.
- Верх: «назад» слева, меню ≡ справа — как у просмотра фото.
- Низ, одна строка/блок: имя файла (мелко, полупрозрачным, сокращение в середине), play/pause, шкала, текущее время / длительность.
- Убрать: перемотку ±5/10 с, «в начало», «следующее/предыдущее».
- Одна подложка-градиент снизу, одна анимация появления/скрытия для всех элементов. Во время воспроизведения скрытие через 3 с (как в 0.2.9), на паузе панель остаётся.
- Иконки и типографика — те же, что у просмотра фото. Портрет и ландшафт — без ручных сдвигов.

**Жесты (громкость и яркость работают одинаково):**
- вертикальный свайп по правой половине — громкость медиа, по левой — яркость;
- зона начала жеста по вертикали — примерно ±30% высоты экрана от центра (полоса 20–80%), чтобы не упираться в шкалу внизу;
- срабатывает только при явно вертикальном движении; горизонтальное — листание файлов (HorizontalPager) не ломать;
- не начинается у краёв: сверху (шторка), снизу (жест «домой»), по бокам (жест «назад», ~24–32dp);
- изменение плавное и относительное: значение меняется пропорционально движению пальца от текущего; один проход не обязан покрывать весь диапазон — жест можно повторить, он продолжает с достигнутого значения. Стартовая чувствительность: проход через всю зону ≈ половина диапазона; подбирается на тестовой сборке;
- яркость — только окна FGallery (`WindowManager.LayoutParams.screenBrightness`), без системных разрешений; при выходе из видео возвращается как была;
- громкость — системная громкость медиа (`STREAM_MUSIC`), но со своим индикатором вместо системной панели;
- индикатор — вертикальная полоска с иконкой у соответствующего края, в стиле панели;
- в режиме уборки двойной тап по видео по-прежнему отправляет в корзину.

#### 1.4 Разрешение RAW — СОГЛАСОВАНО (часть бага Hasselblad)
- Сейчас разрешение берётся из MediaStore (`WIDTH/HEIGHT`). Для 3FR, IIQ, FFF и др. MediaStore его не знает → поле «Разрешение» скрыто.
- Нельзя брать размеры из EXIF IFD0 RAW: у Hasselblad X2D там размеры встроенного превью (3888×2918), а не снимка (11656×8742).
- Решение: для RAW размеры — из LibRaw (`open()` без проявки, `getWidth/getHeight`, с учётом поворота); результат кэшировать (до этапа 5 — в существующем снапшоте/отдельном кэше, на этапе 5 — в каталоге).
- Приёмка: X2D 3FR показывает 11656×8742 (или фактическое значение LibRaw) в «Сведениях» и в быстром EXIF; Canon CR2, IIQ, DNG — корректно.

### Этап 3 (0.3.2) — превью в сетке и очередь декодирования — СОГЛАСОВАНО

**Сейчас (`data/ThumbnailCache.kt`, `ui/GalleryScreen.kt`, `ui/GalleryViewModel.kt`):**
- превью сетки — PNG 720px (~0,5–1 МБ на файл), уровень hq — PNG 1920px; лимита на диск нет;
- `GalleryViewModel.refresh()` после каждого обновления запускает генерацию превью **для всей медиатеки** (+ `prewarmAlbum`), и они делят с видимыми плитками один `Semaphore(2)` (очередь по порядку);
- плитка запрашивает у Coil 960×960 при реальном размере ячейки ~270–360px;
- для нового файла работа делается дважды: Coil декодирует оригинал, параллельно `ThumbnailCache.ensure` декодирует тот же файл, затем Coil декодирует PNG ещё раз.

**Нужно:**
1. **Уровни превью:** микро ~400px JPEG q≈85 для обычных плиток; превью 1920px JPEG q≈90 для крупных плиток мозаики и подложки просмотра. Запрос к Coil — по фактическому размеру плитки.
2. **Один конвейер:** свой Coil `Fetcher`/модель `Thumb(item, tier)`: проверить диск → создать (MediaStore `loadThumbnail` → встроенное превью (EXIF / встроенный JPEG RAW, этап 4) → уменьшенное декодирование) → записать JPEG → вернуть bitmap без повторного декодирования.
3. **Две «кассы»:**
   - видимые плитки: 3 потока, высший приоритет, новые запросы первыми, ушедшие с экрана отменяются;
   - фон: 1 поток, низкий приоритет; на паузе, пока идёт прокрутка (`isScrollInProgress`) или открыт просмотр; продолжает через ~1,5 с покоя; после обновления каталога берёт только новые/изменённые файлы, а не всю медиатеку заново.
4. **Лимиты на диск** с удалением давно неиспользованных (стартовые значения: микро — 500 МБ, превью 1920 — 1 ГБ; вынести в настройки «Кэш»).
5. **Миграция:** новая папка кэша (`v4`), старые PNG-кэши удалить один раз.
6. **Подложка в просмотре:** `placeholderMemoryCacheKey` = ключ превью из памяти (сейчас подложка читается с диска отдельным `AsyncImage`) — без пустых кадров.

**Нельзя сломать:** живые превью видео, анимированные GIF в плитках, превью PDF/SVG/TIFF, плотную сетку без зазоров, режим уборки.

**Приёмка:** на S23 с большой медиатекой — быстрая прокрутка без «серых» плиток дольше короткого мгновения; объём кэша в пределах лимитов; первый запуск после обновления — превью пересоздаются в фоне, сетка работает.

### Этап 4 (0.3.3) — RAW — СОГЛАСОВАНО

**Цель:** RAW открывается почти сразу и сразу резко, без «пиксельной» фазы; всё, что открывается сейчас (включая IIQ), продолжает открываться.

**Сейчас (`data/FullResolutionFiles.kt`):** для RAW всегда полная проявка LibRaw (`setQuality(3)`, AHD) в несжатый PNG (~150 МБ на кадр 5DS R, ~300 МБ на 100 Мп), лимит кэша 1 ГБ; двойной тап заблокирован до готовности. Основное время — сама проявка.

#### 4.1 Порядок показа
1. **Сразу** — подложка из превью сетки из памяти.
2. **Встроенный JPEG камеры**, если его ширина и высота ≥ 90% размеров снимка (с учётом поворота):
   - байты извлекаются **без перекодирования** в кэш `.jpg`;
   - просмотр и зум — как обычный JPEG (тайлы из файла через Telephoto), двойной тап доступен сразу;
   - поворот — из метаданных RAW (во встроенном JPEG его может не быть).
   Пример: Canon 5DS R CR2 — встроенный JPEG полноразмерный 8688×5792.
3. **Встроенный JPEG меньше порога, но больше экрана** (пример: Hasselblad X2D — 3888×2918 при снимке 11656×8742): показывается сразу как промежуточная стадия (по экрану резкий); параллельно в фоне проявка LibRaw; по готовности — бесшовное переключение на полный размер. Зум глубже разрешения JPEG до готовности — с отметкой «детализация загружается».
4. **Встроенного JPEG нет или он меньше экрана** — текущая проявка LibRaw **без изменений** (путь для IIQ и т.п.). Решение принимается по фактическому размеру превью, не по марке камеры.

#### 4.2 Команда «Проявить RAW»
- В меню просмотра для любого RAW. Запускает проявку LibRaw и показывает её вместо JPEG камеры для этого файла. Прогресс и отмена.

#### 4.3 «Сведения»
- Строка: «Показано: JPEG камеры, 8688×5792» / «Показано: проявка RAW (LibRaw)».

#### 4.4 Извлечение встроенного JPEG
- В AndroidLibRaw (`com.github.dburckh:AndroidLibRaw`) метода для встроенного превью нет (проверено по исходникам). Сделать форк (LGPL-2.1, открытый) и добавить JNI-метод: самое большое встроенное превью (список превью LibRaw / `unpack_thumb`), его формат, размеры, поворот. Если превью не JPEG — считать, что его нет.
- androidx `ExifInterface` для этого не подходит: у X2D превью лежит как основное изображение IFD0 и не находится как миниатюра.

#### 4.5 Превью в сетке для RAW
- Источник — встроенный JPEG (через конвейер этапа 3); если его нет — уменьшенная проявка LibRaw в фоновой очереди.

#### 4.6 Кэш
- Встроенные JPEG и проявки — в общем лимите (сейчас 1 ГБ), удаляются давно не открытые. Рассмотреть хранение проявок в JPEG q≈95 вместо несжатого PNG (в 5–6 раз меньше, тайлы из JPEG декодируются быстрее) — решение по замерам.

#### 4.7 Баг Hasselblad X2D (.3FR) — разбор файла `B0004753.3FR`
- TIFF-контейнер; IFD0: встроенный JPEG 3888×2918, ~0,77 МБ, Compression 7, Orientation 8 (вертикальный кадр); SubIFD: RAW 11904×8842 (с краями матрицы), 16 бит без сжатия, ~210 МБ. Рабочая область по паспорту — 11656×8742.
- Причины: нет превью в сетке — для RAW нет LibRaw-пути в сетке, а ExifInterface превью не видит; нет разрешения — MediaStore не знает размеров (решается в п. 1.4).
- **Риск памяти:** полная проявка 100 Мп требует ~0,8 ГБ рабочей памяти, итог ~300 МБ на диске. Замерить на S23; при нехватке — проявка частями или уменьшенная для просмотра + полная по требованию.

#### 4.8 Приёмка (реальные файлы, S23)
- Canon 5DS R CR2: резкое изображение < 1 с, зум до максимума без пиксельной фазы, вертикальные кадры повёрнуты верно.
- Hasselblad X2D 3FR: превью в сетке, мгновенный резкий показ по экрану, переключение на полную проявку, разрешение в сведениях.

- DNG, TIFF: без регрессий. «Проявить RAW» работает и отменяется. В «Сведениях» видно, что показано.

#### 4.9 Редактор
- Редактор (отдельный проект) всегда работает с данными RAW, а не со встроенным JPEG.

### Этап 5 (0.4.0) — каталог и пошаговое сканирование — СОГЛАСОВАНО

**Сейчас:**
- при запуске сразу показывается снапшот `library_snapshot_v1.json` (хорошо);
- затем полный `refresh()`: MediaStore по всем томам + `DocumentLibrary` + `DriveLibrary.load()`, который при доступе ко всем файлам обходит **всё** хранилище файл за файлом (`walkTopDown`);
- **любое** изменение MediaStore (`ContentObserver` в `MainActivity`, задержка 300 мс), в том числе от собственных операций FGallery, запускает этот полный цикл заново + перезапись JSON + перезапуск генерации превью.

**Нужно:**
1. **Каталог в SQLite (Room)** вместо JSON: файлы, папки (путь, время изменения, время последнего сканирования), носители. Сразу заложить поля под дубликаты (этап 6): размер, быстрый хеш, полный хеш, перцептивный хеш, EXIF-ключи (время съёмки, камера, размеры, у RAW — из LibRaw).
2. **MediaStore пошагово:** запоминать `MediaStore.getGeneration(volume)` и `getVersion(volume)`; забирать только строки с `GENERATION_MODIFIED > last`; удаления — сравнением списка `_ID` (дёшево); смена `getVersion` → полная перечитка тома. Android 10 (API 29) — полная перечитка MediaStore (без обхода файлов).
3. **Обход файлов** — только там, где MediaStore не индексирует (USB и неиндексированные носители, расширения вне MediaStore): перечитывать только папки, у которых изменилось время изменения; новые папки — целиком.
4. **Собственные операции** (перемещение, переименование, удаление, корзина, кадрирование) обновляют каталог напрямую; уведомления наблюдателя от них не запускают пересканирование. При частичном завершении операции — сверка затронутых папок.
5. **Полный проход — страховка:** в фоне с низким приоритетом при холодном старте, по свайпу вниз в сетке, при подключении носителя.
6. **Контроль:** в тестовой сборке выполнять пошаговое и полное сканирование и писать расхождения в лог.

**Риски (файлам ничего не грозит — сканирование только читает):**
- пропущенное изменение не исправится до полного прохода (новый файл не появится, удалённый «висит»);
- FAT32/exFAT: время изменения папки с точностью 2 с и обновляется не всеми драйверами;
- перезапись файла с тем же именем не меняет время папки (ловится через MediaStore);
- пересоздание базы MediaStore сбрасывает счётчик — ловить через `getVersion`;
- каталог используют альбомы, сортировка, корзины по носителям, запоминание отключённых носителей, перемещение — переезд с JSON затрагивает всё это.

**Тесты:** добавить / удалить / переименовать / переместить файл другим приложением; файл, перезаписанный с тем же именем; подключение/отключение USB и SD; массовое перемещение 2500 файлов; IIQ/3FR/FFF находятся; корзины по носителям и записи отключённых носителей сохраняются.

### Этап 6 (0.4.x) — поиск дубликатов — СОГЛАСОВАНО

**Что ищем:** точные копии; один и тот же снимок в другом разрешении; кадрированные копии оригинала.

**Что НЕ дубликаты:**
- RAW + JPEG одного кадра (съёмка RAW+JPEG) — показываются как пара, к удалению не предлагаются;
- снимки после цветокоррекции и/или ретуши, даже если похожи на оригинал; кадрированная и при этом обработанная копия — тоже не дубликат;
- разные кадры серии (другая поза модели и т.п.).

**Как определять:**
- отпечатки из каталога (этап 5): размер → быстрый хеш (начало+конец файла) → полный хеш только при совпадении первых двух; перцептивный хеш по превью сетки; EXIF;
- пересчёт только при изменении файла; перемещение не пересчитывает;
- расчёт — в фоновой «кассе» (этап 3), на паузе при прокрутке/просмотре;
- «тот же снимок в другом разрешении»: очень близкий перцептивный хеш + те же пропорции + совпадение времени съёмки/камеры (если есть) + сравнение уменьшенных копий;
- «кадрированная копия»: совпадает с участком оригинала по пикселям с допуском только на пересжатие JPEG и масштаб;
- изменение цвета/тона по кадру или локальные отличия (ретушь) сверх этого допуска → не дубликат;
- пороги подбираются на тестовом наборе пользователя (оригинал, его кроп, его цветокоррекция, его ретушь, серия с разными позами).

**Что оставлять — «больше признаков исходника → выше приоритет»:**
1. формат: RAW (включая DNG) > TIFF > HEIC/HEIF > JPEG;
2. большее разрешение (кроп всегда проигрывает оригиналу);
3. меньшее сжатие (оценка качества JPEG по таблицам квантования);
4. больший вес файла;
5. более ранняя дата (съёмки, затем создания файла);
6. полный EXIF камеры выше урезанного/отсутствующего.

Приложение **предлагает**, пользователь подтверждает. В каждой группе видно, почему предложен именно этот файл. Удаление — в корзину FGallery.

**Где искать:** по умолчанию вся память (все носители); можно выбрать одну или несколько папок.

## 3. Редактор фото — отдельный проект
- Разрабатывается отдельно (отдельный модуль + тестовое приложение), чтобы не пересобирать галерею. Состав функций — в отдельном обсуждении (база: экспозиция, цвет, температура, резкость; для RAW — работа с данными RAW).
- Контракт с галереей: на вход — файл (URI), на выход — сохранённая копия (URI). Оригинал не изменяется; для RAW — только копия.
- В галерее ничего не делать, кроме будущей кнопки вызова.

## 4. Подготовка к публикации (Google Play, RuStore) — РЕШЕНИЕ НЕ ПРИНЯТО

Ниже — предварительные рекомендации для будущего обсуждения. **Не реализовывать** до решения пользователя.
